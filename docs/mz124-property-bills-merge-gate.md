# MZ-124 房源账单合并检查

## 合并会怎样被拦住

继续用 Dev 已设为必过的 GitHub Actions `Fast Regression`。Dev PR 的变更涉及房源账单、共用前端/接口/权限，或检查本身时，先运行原有快检，再在 GitHub runner 的独立本机 PostgreSQL 和真实页面上运行账单脚本。只使用合成房源和账单；不携带 Neon 或部署凭据，不需要 Docker。检查使用 GitHub 给该 PR 的测试合并版本，不接受另一提交的测试结果。

最后一步不因前面失败或跳过而跳过。只有房源账单确实不受这次 PR 影响，才能报告「不适用」；必须运行却失败、跳过、取消、没有结果或结果属另一提交，都让同一个必过检查失败。分类失败或缺失也失败。仅账本变更仍无需安装依赖；现有完整发布检查的事件安排不变。

## UI 与正式发布

这一道是功能合并检查，不拿 GitHub Linux 的截图和用户批准的 Mac 截图直接做像素比较。保留四张批准原图，生产或 CI 环境不覆写。将来若启用 CI 视觉门槛，用固定环境重新拍四张并核对外观；视觉批准与复查按 MZ-124 的 UI 基准单独记录。

## 远端验证步骤

1. 只提交房源账单测试工具（依赖）与这一道合并检查。按仓库规则精确审查提交、分支和授权。不顺带提交其它 124 工作。
2. 在不合并的试验 PR 上分别观察必过的 Fast Regression 成功、故意失败、必须跑但步骤跳过三种。失败或跳过时，必须看到合并被 GitHub 禁止，而不是只看到脚本红灯。
3. 查看 Vercel/Render 对该试验 PR 或分支的自动预览影响，再开 PR；如果不能避免用户未批准的预览，停下并另行确认。验证完成只关闭试验 PR，不合并、不部署。不要用尚无新任务的旧 PR 成功状态冒充这次证据。
